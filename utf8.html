00–7F128 values · 50%

0xxxxxxx. A complete character on its own: U+0000–U+007F. Also the only range valid at any position.

80–BF64 values · 25%

10xxxxxx. Payload of every multi-byte sequence — must follow a lead byte, meaningless alone. Consumed 1–3 times per sequence.

C0–C12 values · 0.78%

110xxxxx leads that can only start overlong encodings of ASCII codepoints. Never valid.

C2–DF30 values · 11.72%

110xxxxx. Starts a 2-byte sequence (one continuation follows): U+0080–U+07FF. Latin-1 supplement, Greek, Cyrillic, Arabic, Hebrew…

E0–EF16 values · 6.25%

1110xxxx. Starts a 3-byte sequence (two continuations): U+0800–U+FFFF. Most of the BMP.

Edge constraints live in the second byte: E0 needs ≥ A0 (anti-overlong); ED needs ≤ 9F (blocks surrogates U+D800–U+DFFF).

F0–F45 values · 1.95%

11110xxx. Starts a 4-byte sequence (three continuations): U+10000–U+10FFFF. Everything outside the BMP — emoji included.

F0 needs second byte ≥ 90 (anti-overlong); F4 needs ≤ 8F (nothing above U+10FFFF).

F5–F73 values · 1.17%

Same 11110xxx shape as F0–F4, but the payload lands past Unicode's limit: U+140000–U+1FFFFF. Well-formed in the original spec; rejected by modern UTF-8.

F8–FB4 values · 1.56%

111110xx. 5-byte leads: U+200000–U+3FFFFFF. Original spec only — modern UTF-8 stops at 4 bytes.

FC–FD2 values · 0.78%

1111110x. 6-byte leads: U+40000000–U+7FFFFFFF — the top of the original design, which serialized all of UCS-4 (231 codepoints).

FE–FF2 values · 0.78%

1111111x — the lead-bit scheme runs out: no 0 remains to separate the marker from the payload. Never valid in any version.

Two specs are layered here. Modern UTF-8 (RFC 3629, 2003): sequences up to 4 bytes, lead bytes up to F4, no overlongs, no surrogates — because Unicode stops at U+10FFFF. The original design (Thompson & Pike, 1992; RFC 2279, 1998) serialized all of UCS-4: 5- and 6-byte sequences, leads up to 0xFD, codepoints up to U+7FFFFFFF. The boxes past F4 follow that original scheme — which is also what the utf8(7) man page describes. For contrast, lenient decoders accept even more: Neovim's built-in vim.str_utf_pos consumes C0- and F5-led sequences as complete. Widths are exact fractions of 256 (e.g. C2–DF = 30/256 = 11.71875%).
